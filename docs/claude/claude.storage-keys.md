# Storage Keys Reference

| Key | Storage | Purpose |
|-----|---------|---------|
| `ilap_ignored_count` | local | Ignores this extension has performed and NOT rolled back — +1 on every confirmed ignore POST, whatever fired it (MI at drain time, EQ, DQ, and the curator drain via `bumpCount`, count-only), −1 on every confirmed `remove=1` POST (`dropCount`, in the drainer's one undo branch — droplist undo, solo-un-ignore gesture and badge click all drain through it). Both directions count the POST, never the intent: a dedupe skip, a region-lock skip or a refusal never posted, so it never moves. Still not the size of Steam's list — ignores made before install are not in it, which is also why the decrement is floored at 0 (rolling one of those back has no increment of its own to take back). The popup renders it as a link to `/account/notinterested/`, where the two numbers can legitimately differ |
| `ilap_ignored_history` | local | Last 20 ignored games. NAMED ignores only (MI/EQ/DQ) — the curator drain deliberately stays out: it enumerates appids with no names, and one job would flush the whole list. An un-ignore does not rewind it either: this is a log of what was ignored lately, and a rolled-back entry still happened (what is *undoable* lives in `ilap_ignore_log`) |
| `ilap_last_ignored_name` | local | Most recent game — written by the same named paths as the history, and equally untouched by the curator drain and by rollbacks |
| `ilap_shortcut_key` | local | Default ignore shortcut. Same vocabulary as the other two binding keys — the two swipes, `'zigzag'` (the circle), the three modifier-clicks — because any action may take any binding |
| `ilap_platform_key` | local | Already-Played shortcut, or `'off'`. Same vocabulary as above |
| `ilap_unignore_key` | local | Solo un-ignore binding: `'zigzag'` (default — hold right-click and draw a circle or a right-left zigzag over the capsule), any binding the ignore selects offer (`'swipeRight'`/`'swipeLeft'`/`'ctrlKey'`/`'shiftKey'`/`'altKey'`), or `'off'`. No legacy shim, unlike `normalizeShortcut`'s for the two ignore keys: this binding ships with its first release, so no build has ever written another vocabulary here. An unrecognised value (a hand-edited key) falls back to the default rather than becoming an inert binding: the content script clamps against `ManualIgnore.UNIGNORE_KEYS`, the popup select (which cannot reach that module) against its own `<option>` list. The vocabulary is IDENTICAL to `ilap_shortcut_key`/`ilap_platform_key`, so all three selects are cross-guarded against each other by disabling a value another one has taken (`syncSelectors`, asserted in `tests/popup/settings.spec.js`): resolution is first-match-wins in both `EventParser.parseClick` and `SwipeGestureDetector._fire`, with the ignore bindings resolved FIRST, so a value bound twice by a hand-edited storage key costs the rollback, not the ignore. `'off'` drops the rebindable gesture only: a **click on the IGNORED badge, either button, always un-ignores** — two delegated listeners in `manual-ignore/main.js`, answering to no setting but the master toggle (free, because the badge already swallowed plain clicks so it could not navigate). That is why the popup labels the option `shortcut_off_badge_only` ("Off - only Click on Badge") instead of the ignore selects' bare "Off". The zigzag is classified from the X axis ONLY, the same rule the swipe uses — so a clockwise and a counter-clockwise circle are indistinguishable and both fire; telling them apart would need `dy`, which `decisions.md` rules out for these gestures. That is also why a flat left-right zigzag fires the binding: same motion to the detector, and genuinely useful on a capsule too short to circle over. Every locale's `shortcut_zigzag` label names the CIRCLE alone — one gesture per label, in a 320px row — so the zigzag lives in exactly one place the user can find it: the `tooltip_unignore_gesture` hover hint on the "Un-ignore:" row. That hint names no ROTATION direction on purpose. Both directions fire, but the glyph beside the label has to be drawn some way round (counter-clockwise, for the undo convention), and spelling out "either way" — true as it is — made the icon look like it meant something and left the reader asking which way. Saying nothing lets them copy the glyph and be right, with the other direction working anyway. A native `title` (like the Discovery-Queue rows), NOT one of the popup's own drawn tips: the browser paints it outside the document, so the panel's `overflow: hidden` cannot clip it and it needs no entry in `tests/popup/tooltips.spec.js`. It is also resolved BEFORE the swipe: its legs clear the distance threshold on their own, so both would otherwise fire from one gesture |
| `ilap_master_enabled` | local | Global on/off |
| `ilap_dq_active` | local | Cross-tab cap on concurrently-active Discovery-Queue automators (`window.ILAP.Discovery.Registry`): a heartbeated owner map `{ ownerId: expiresAt }`, TTL-reclaimed like the curator lease so a closed tab frees its slot. `DiscoveryQueueController` claims a slot on Start (refuses with a transient "max {n} running" button message when ≥`CAP`=2 other live owners fill it), renews every 3 s while running, releases on stop. A UX bound, not a safety one — the `ilap_ignore_gate` governor already caps the aggregate POST rate; this just stops silent stacking of DQ loops. Cross-tab residual: no CAS, so two tabs racing can briefly make 3 active (accepted). Also accepted: Chrome throttles a backgrounded tab's timers, so a hidden DQ tab's heartbeat can lapse and its slot expire while its automator keeps ignoring (background loops run, slower) — the cap can undercount, but the rate gate still bounds the aggregate POST rate |
| `ilap_ignore_gate` | local | Aggregate ignore-POST rate governor (`window.ILAP.IgnoreGate`): a single last-reserved-slot timestamp. Every ignore SOURCE — the curator drainer (bulk curator jobs, `remove=1` undo jobs and deferred manual-ignore jobs alike, in a tab or in the service worker), the EQ automator, and the DQ icon click (which makes Steam's own page JS fire the ignore POST — confirmed, so DQ is NOT request-free) — calls `reserve()` before emitting an ignore; it advances this timestamp by ~500 ms + jitter (350 ms floor) via a per-context serialized RMW, so the aggregate rate across all tabs/sources of a profile stays ≤ ~2/s and stacked sources collapse into one paced stream. `reserve()` also STOPS (no slot) when `ilap_master_enabled=false` (closes audit #1: master vs drainer) or when there is no LIVE Steam session (closes audit #2: dead session must not burn work). The session check is deliberately NOT "is there a `sessionid` cookie?" — Steam hands that cookie to anonymous visitors too (it is a CSRF token, not a credential), so the old presence check was true on every store page of a signed-OUT browser and slots were granted for POSTs that could only 400; the cookie stays as the cheap precondition and the verdict comes from `SteamAuth`'s two signals: a signed-IN store header settles it for free (trusted in the positive direction only), otherwise one live `/account/` probe, cached in memory for 60 s (the SW has no DOM and always probes). Both stop conditions are RE-CHECKED after the pacing wait (a master flip / logout mid-wait can't be followed by one more ignore — DQ additionally re-checks `isRunning`, the drainer re-reads the job status, so a Stop/Pause during the wait stops before the POST). A stored slot further than `MAX_AHEAD` (30 s + `PENALTY_MAX`, since a 429 penalty from `ilap_ignore_gate_penalty` can legitimately push the slot minutes ahead) in the future is clock skew (manual clock change, resumed VM) and is clamped to now, not waited out. Manual ignore IS gated now: a swipe no longer fires an instant ungated POST but enqueues a `type:'mi'` job the drainer paces through this same governor, so the extension has no ungated ignore path left. `reserve()` takes an optional `{ foreground: true }` (EQ / DQ — see `ilap_ignore_foreground_at`); a background caller without it yields while visible work is recent. `stopVerdict()` — the same master/session check `reserve()` applies — is also exported, and the queue drainer calls it BEFORE opening a pass: a stopped extension would otherwise pay a `dynamicstore/userdata` GET per tab per standby tick (and keep the SW's retry alarm armed) only to be refused a slot afterwards. Cross-tab residual: no CAS, so two tabs can rarely share a slot — accepted, same class as the stats/queue RMW races |
| `ilap_ignore_gate_penalty` | local | Rate-limit backoff for the ignore governor (`{ until, level }`), written by `IgnoreGate.reportRateLimited()` when the ignore endpoint answers **429** (`SteamAPI.ignore` now resolves `{ ok, rateLimited, retryAfterMs, status }` — `status` is the raw HTTP code (0 when the request never completed), read only by the curator drainer's 400-classifier so a timeout/5xx can't be mistaken for a region-lock refusal; the drainer ends its pass without burning `fails` on the appid, EQ reports and stalls — DQ can't see HTTP status, its POST is fired by Steam's page JS). `reserve()` folds an active `until` into the next slot, so every source in every tab goes quiet together; a source already HOLDING a reserved slot still fires it (accepted residual: ≤1 in-flight ignore per source after a 429). Escalation: 5 s doubling to a 5 min cap (`PENALTY_BASE`/`PENALTY_MAX`), honouring a numeric `Retry-After` up to the same cap; consecutive 429s escalate while each lands within `PENALTY_DECAY` (60 s) of the previous penalty's end, a quiet spell resets to level 1. An `until` further than `PENALTY_MAX` in the future is corruption/skew and is ignored (same rationale as the gate's `MAX_AHEAD`, which grew to 30 s + `PENALTY_MAX` so a legitimate penalty-pushed slot isn't clamped as skew). Cross-tab residual: no CAS, two tabs reporting the same 429 can double-escalate — accepted, over-backing-off is the safe direction |
| `ilap_ignore_foreground_at` | local | Timestamp of the last ignore reserved by a VISIBLE source — EQ or DQ, which pass `{ foreground: true }` to `IgnoreGate.reserve()`. A background reservation (the queue drainer, no flag) is refused with `reason:'yield'` while this stamp is younger than `YIELD_MS` (2.5 s, a little over one gap+jitter), so a stream of visible ignores keeps the drainer paused continuously while a lone one stalls it only a couple of seconds. Purely a priority split INSIDE the shared budget — it never raises the aggregate rate; the yielded pass retries on the standby tick / SW alarm. Manual ignore is not a foreground source any more: a swipe enqueues a `type:'mi'` job that the drainer picks FIRST (`_pickJob`) but still paces through the gate |
| `ilap_q_master` | local | Queue automator enable |
| `ilap_q_next` | local | Auto-advance after ignore |
| `ilap_q_mode` | local | `"bad"` or `"all"` |
| `ilap_dq_open` | local | SETTINGS panel: "Your Discovery Queue" subcategory expanded (default collapsed). Restored on each settings render, persisted on `<details>` toggle. Mutually exclusive with `ilap_mi_open` — opening one collapses the other |
| `ilap_mi_open` | local | SETTINGS panel: "Manual Ignore" subcategory expanded (default collapsed); mutually exclusive with `ilap_dq_open` |
| `ilap_session_map_v2` | session | appid → reason map |
| `ilap_queue_active` | session | Explore queue ACTIVE intent |
| `ilap_queue_ff` | session | Explore queue fast-forward intent |
| `ilap_queue_nav_token` | session | 15 s navigation authorization token |
| `ilap_curator_queue` | local | Ignore-task jobs (≤3, +1 for each of the two gesture jobs), user-owned fields only (all writes via `Store.mutateQueue`). **Fourth type, `'miundo'`** (`curatorId:'miundo'`, id `job_mi_undo`, cap `MIUNDO_MAX=200`): the solo un-ignore gesture's twin of the MI job, auto-filled and auto-deleted the same way, and the drainer's TOP priority — ahead of the MI job, which is itself ahead of all background work. The two gesture jobs cannot share one bucket and be fair: `_drainJob` runs a job to its end and the bucket resolves by array position, so whichever job happened to sit earlier drained entirely before the other was looked at — behind a 200-entry MI backlog at ~0.6 s a POST that is minutes of a badge left dimmed. A rollback is the later intent by construction (you can only take back a game you already swiped) and it is the one holding a provisional mark on screen, so it wins; the reverse starvation is cheap, since nobody gestures hundreds of rollbacks and the MI badge is already painted. It is a SEPARATE job rather than a flag on an MI entry because direction is a property of the JOB — the drainer reads `isUndo` from `job.type` and it governs the whole pass (strict vs lenient userdata read, the live login probe on an empty set, the INVERTED dedupe, the "last user intent wins" rule), so a mixed job would force MI permanently onto the strict path. Because it auto-fills, its entries carry their OWN gesture time in `meta[appid].ts` instead of a job-level `snapshotTs`: one shared ts would be the moment the FIRST gesture created the job, and a game ignored after that then un-ignored by a later gesture would read as "re-ignored after the snapshot" and be skipped. Removing it with entries still undrained pulses `ilap_undo_failed` with `reason:'removed'` (nothing to un-badge — the games stay ignored — but the rollbacks are gone, so the pending marks come off; silent, because the user dropped the job themselves). Filling it past `MIUNDO_MAX` raises its OWN `miundo_queue_stuck` card, not the MI one, which names the ignore job by hand and would send the user to the wrong row. Three older job types: curator jobs (appids + filter + status: enumerating/pending/paused); at most ONE undo job (`type:'undo'`, `curatorId:'undo'` — the pseudo-id keys its drain lease — plus a STATIC `appids` snapshot from `ilap_ignore_log` and `snapshotTs`, the "last user intent wins" boundary: the drainer skips an appid re-ignored after it); and at most ONE Manual-Ignore job (`type:'mi'`, `curatorId:'mi'`, id `job_mi`). The MI job is AUTO-FILLED: a swipe no longer fires an ungated instant POST — it optimistically badges the game and `Store.enqueueMi` appends `{appid}` to this job with a per-appid `meta[appid]={name,reason}` (the drainer POSTs the right reason and stamps Last Ignored at drain time); `appids` stays a plain string array for the generic paths. A re-swipe of an appid still in the PENDING tail is de-duped (no double-POST) but REFRESHES its meta — the per-tab session map only blocks a re-swipe inside ONE tab, so a second tab can swipe the same game with the other reason and paints the badge its gesture chose; last gesture wins, or the queued POST would contradict the badge on screen. A solo un-ignore gestured at a game whose ignore is still PENDING sets `meta[appid].cancelled` instead of queueing a rollback (`Store.cancelMiEntry`) — tried FIRST, ahead of both the un-ignore cooldown and the logged-out gate, because a cancel emits no POST in either direction and so has nothing to brake and needs no session; behind the 2 s cooldown the branch was near unreachable, the gate pacing at MIN_GAP+jitter (~0.5–0.8 s) meaning a lone queued swipe is already sent well before the brake lifts and every "wrong game" cost a real `remove=1`. The drainer steps over the entry — checked before it spends a rate slot and AGAIN on the fresh record after the gate wait, which is where the cancel usually lands — so neither POST goes out and nothing is logged or counted for an ignore that never happened. It MARKS rather than splices because `appids` indices are the cursor's coordinate system: removing one would slide an innocent entry under a cursor already advanced past it. `cancelMiEntry` re-reads the cursor after the mutation and reports false if the drain got there first, so the caller falls back to a real rollback instead of un-badging a game that IS ignored. One window the cursor cannot describe: it advances only once the POST has RETURNED, so a gesture landing mid-request is told it cancelled an ignore that was in fact already sent (a slow POST is all it takes) — the tab drops the badge for a game Steam is about to ignore. The drainer closes it from the other side: after advancing the cursor it re-reads the mark and, if the entry was cancelled meanwhile, queues the un-ignore itself (`_compensateCancelled`). Checked AFTER the cursor moved, which closes the window rather than narrowing it — a cancel arriving any later reads the advanced cursor, is refused, and the tab queues the rollback. The correction is a real rollback, not a repainted badge: the ignore did land, and stays counted and logged exactly as it happened. A re-swipe rewrites the whole meta entry, which clears the mark by construction. `MI_MAX=200` caps it (a swipe past = silent no-op); it is one of the two types allowed to exceed the 3-job cap (its own slot, second drainer priority behind `miundo` via `_pickJob`), and auto-deletes when drained empty. Drain-time only (§7): `saveStats` + `log.append(source:'mi')` are gated strictly to MI so curator/undo never touch Last Ignored. Undo jobs get the same lease/handoff, cursor key, Pause/Remove and gate pacing; the drainer branches on the type to POST `remove=1` with INVERSE userdata dedupe (a skip also marks the log entries `undoneAt`). Because the inverse dedupe reads "not in the set" as "already rolled back", an undo pass STOPS (job intact, retried later) on a failed strict userdata read, and an EMPTY set is only trusted after a live `SteamAuth.probeLogin()` — a logged-out userdata read returns the same empty defaults and would otherwise skip-burn the job with zero requests. Per-appid the same trust is time-gated: `rgIgnoredApps` lags a fresh ignore POST by seconds, so an appid absent from the set but whose newest live `ilap_ignore_log` ts is within `UNDO_FRESH_MS` (~15 s) is un-ignored anyway (`remove=1` is idempotent) instead of skip-marked, so a just-ignored game staged into an undo isn't stranded in the ignore list with its log entry burned out of the undoable pool |
| `ilap_ignore_log` | local | Undo data source (`window.ILAP.IgnoreLog`): append log of every ignore the EXTENSION performed — `{ appid, name?, ts, source: mi\|eq\|dq\|curator, curatorId?, undoneAt?, skipped? }`, FIFO-capped at 5000. A `skipped` marker records an appid a drain stepped over WITHOUT ignoring it (a refusal, NOT an ignore) — inert for every undo selector, kept as the durable "the job wasn't a full done" trace: `'unavailable'` for a region-locked appid (classified 400), `'failed'` for one that lost every retry on a live session. That second value is the ONLY trace of the `MAX_FAILS` path — the per-job `ilap_curator_skipped_<id>` counter dies with the job and the push cards need a listening tab, which the SW route has none of by design (no notification surface was built for it: see `decisions.md` 2026-07-30). Costs no extra volume — an appid that had landed would have been appended here anyway. MI entries carry the swipe-time `name` on both paths; UNDO jobs never write a `skipped` entry, because a failed rollback's log entry must stay live so the next "undo the last N" retries it. Written beside `saveStats` by the MI/EQ/DQ stats adapters (they pass the appid through) and by the curator drainer per confirmed ignore (appid-only — enumeration has no names). Steam's own `rgIgnoredApps` carries no dates, so count- AND time-scoped undo both operate on OUR `ts`. The undo drainer marks rolled-back entries `undoneAt` (kept, not deleted) so a later undo can't re-undo them and the curator droplist can warn on a re-stage within 48 h (`lastUndoneForCurator`); inverse-dedupe skips (appid already un-ignored elsewhere) are marked too, so stale entries can't inflate the undoable count forever. Undo deliberately does NOT touch `ilap_ignored_count`/history (curator drains never incremented them — a decrement would corrupt). Serialized-RMW writes; cross-tab no-CAS residual accepted (at worst one log entry lost, cosmetic). This is a drain-progress key for the popup render path (written 1–3×/s mid-drain → light re-render only) |
| `ilap_curator_cache` | local | Per-curator enumerated apps cache (TTL 7 d, LRU ≤10) |
| `ilap_curator_cursor_<jobId>` | local | Drainer-owned per-job progress cursor (single writer = lease holder; removed with the job). `Store.setCursor` refuses the write when the job is no longer in the queue, so a remove racing a resolve/drain iteration can't recreate (leak) the key after its only cleanup path ran |
| `ilap_curator_skipped_<jobId>` | local | Drainer-owned per-job count of appids skipped as permanently refused (400 classified as region-locked via an appdetails probe: no store object in the account's region). Same single-writer/partitioning/cleanup discipline as the cursor key; surfaced in the queue applet's job row |
| `ilap_curator_lock_<id>` | local | Per-job drain lease `{ owner, expiresAt }` (single-drainer handoff); a live lease is also the UI's derived "running" signal |
| `ilap_curator_pulse` | local | Timestamp written when a job finishes; widget watches it to blink once (finished jobs are removed, not kept) |
| `ilap_unignored` | local | `{ appids: [...], ts, reason }` pulse written whenever games stop being ignored (`Store.signalUnignored`): after EACH confirmed `remove=1` of an undo drain (`reason:'undo'`), when a deferred Manual-Ignore POST is dropped for good — region-locked appid or every retry refused (`reason:'failed'`), and when an MI job is REMOVED from the queue applet with entries still undrained (`reason:'removed'` — silent, the user asked for exactly this; the whole tail from the cursor on — the `mi_queue_stuck` card tells the user to do exactly that, and those POSTs will now never fire), and when a solo un-ignore gesture CANCELS a swipe that was still queued (`'undo'` — nothing was ever ignored, so there is nothing to tell the user). That last one goes through the pulse rather than un-badging in place precisely because badges are per-tab AND persisted in `sessionStorage`: a second tab that swiped the same game would otherwise keep showing IGNORED for a swipe that was taken back, across reloads, until the tab was closed. Every Manual-Ignore content script watches it via `onChanged` and clears those games' on-page IGNORED badges (`BadgeRenderer.unrender` + drop from the per-tab `sessionMap`) — only for appids THIS tab badged. `'failed'` additionally raises the shared push card (`mi_ignore_failed`), once per burst, so an optimistic badge never just evaporates minutes after the swipe; `'undo'` and `'removed'` stay silent, the user asked for both. Listeners also accept the pre-list `{ appid }` payload, so an already-open tab still running the OLD content script across an extension update does not keep a badge that lies until it is reloaded. The payload is a LIST: the drainer still pulses one appid at a time (so a badge rolls back as its game does), but a removed job drops its whole tail in one write rather than N onChanged fan-outs. `removeJob` reads the cursor AFTER the queue write — `setCursor` refuses once the job is gone, so the drained head can't be un-badged by a concurrent advance |
| `ilap_undo_failed` | local | `{ ts, reason }` pulse (`Store.signalUndoFailed`), the mirror image of a `'failed'` un-badge: a rollback the user asked for is not going to happen, so the game stays ignored. No appid — nothing on the page is wrong (the badge says "ignored", which it is); the point is that the rollback silently didn't happen, and the only other trace was a job-row skip line that dies with the finished job. `reason` carries the SAME distinction as `ilap_unignored`'s: `'failed'` (an UNDO job's `remove=1` was permanently refused for a region-locked appid, or failed every retry) raises the card; `'removed'` (the user dropped the whole `miundo` job from the queue applet) clears the pending marks and stays SILENT, because "Steam refused some rollbacks" would blame Steam for what the user just did. Any store tab turns a `'failed'` pulse into one throttled `undo_failed` push card (the Manual-Ignore content script owns the listener — it is the only module on EVERY store page with a push card; the curator module no-ops outside a curator page). It is also what takes the pending mark off badges whose SOLO un-ignore fell through: the pulse carries no appid, so every pending mark in the tab clears — worst case a droplist undo's failure un-dims a solo gesture that is still queued, which leaves the badge saying the true thing either way. Like the MI `'failed'` card, a drain with no tab open loses the notice (deliberate — `decisions.md` 2026-07-30) |
| `ilap_sw_sid` | local | Cached `sessionid` for the SW drainer (`src/background.js`, Chromium only): under `permissions: ["storage"]` the service worker cannot read `document.cookie`, so the curator-drainer boot block caches the cookie here on every store page. Change-only write (a same-value write would wake the SW via `onChanged` for nothing); written at page boot rather than enqueue time so a re-login refreshes it. The SW mirrors it into memory (the gate's `getSessionID` reads it synchronously); no value → the gate's `no-session` stop applies. Firefox: written but unconsumed (no SW drain there — unverified fetch behavior) |
| `ilap_sw_halt` | local | SW-drain circuit breaker: set true by the SW after 2 CONSECUTIVE failed ignore POSTs (429s excluded — that's the gate penalty's job; 400s classified as region-locked appids excluded too — they're per-appid, not systemic, and are skipped/counted instead, so the "open a store page" hint stays truthful). A stale cached sid (re-login with no store tab open) or a missing `Steam_Language` cookie fails EVERY POST, and the drainer's `MAX_FAILS` (3) skip would then burn appids one by one; the halt engages at 2 — before the first skip — and the SW's gate wrapper refuses every slot while it's set. Cleared by the drainer boot on any store-page visit, which also re-caches the sid (one user action fixes both causes; the popup queue applet shows a `queue_sw_halt` hint pointing there). Tab drainers ignore the flag — their cookie jar is live |
| `ilap_widget_expanded_ts` | local | Widget launcher state: 0/absent = collapsed to the chevron tab (default); >0 = expanded, value = last-activity timestamp (bumped on widget clicks, throttled 5 s). Any tab's 60 s idle timer stashes the launcher; an open panel re-bumps instead |
| `ilap_widget_pinned` | local | Widget pin badge (launcher corner, shown on hover): true = launcher pinned out — idle timers re-bump instead of stashing, stale-timestamp mounts stay expanded — until the user unpresses the pin. | `ilap_surface_mode` | local | Which surface hosts the popup UI: `'widget'` (default) = on-page shadow-DOM widget; `'popup'` = the `chrome.action` toolbar popup (`ui/popup.html`). In popup mode the on-page widget parks to a ghost-chevron beacon. The mode ONLY decides where the UI lives — since the SW drain (`src/background.js`) the queue progresses with no Steam tab, so the old "popup mode ⇒ empty curator queue" invariant and the popup-mode staging locks (curator button, undo droplist) are REMOVED: switching is free in both directions with a busy queue, and staging works from either surface (the deleted `curator_locked_popup`/`surface_popup_blocked` i18n keys died with the locks). The widget-mode toolbar stub shows an aggregate queue progress line + the `ilap_sw_halt` hint instead of the full applet. The Steam desktop client (CEF, no toolbar) forces widget regardless of the stored value via `Surface.resolve(stored, navigator.userAgent)` — the key is never overwritten. Escape hatch: **Ctrl+Alt+Shift+I** on any store page writes `'widget'`. **Default set at install/update by `src/migrate.js` (loaded into the background context — on Chromium via `importScripts` in `src/background.js`, on Firefox as the sole background script; the whole background is swapped out in `--test` builds):** a fresh install persists `'widget'`; an update from the old popup-only build (key absent) is migrated to `'popup'` so existing users keep the toolbar popup they know. **Sign-in push:** when the surface flips popup→widget while logged out, the widget shows a 10 s on-page `.ilap-push` — a bottom-right toast styled like the shared push card `.ilap-toast` (icon + text, blue left-accent, slide-up) but living inside the widget's shadow root and click-dismissable, so it is its own element rather than a `src/toast.js` call, with the same copy as the launcher's login tooltip (`widget_login_required`) — so the user knows the on-page surface needs a Steam sign-in. The launcher's own login tooltip (`.ilap-login-tip`) is offset left of the full-width launcher (`right: ICON+8`) so it doesn't sit over the icon |
| `ilap_intro_glow` | local | New-install chevron beacon, armed by `src/migrate.js` on a FRESH install only (alongside `ilap_surface_mode:'widget'`): while true, the collapsed chevron keeps the steady blue rim (`.restored`) and radiates the gold halo (`.gold`) in 10 s bursts once a minute (`INTRO_BURST_MS`/`INTRO_CYCLE_MS` — a non-stop pulse would nag) — a first-time user has never seen the on-page surface and the slim tab is easy to miss.
