# Storage Keys Reference

| Key | Storage | Purpose |
|-----|---------|---------|
| `ilap_ignored_count` | local | Ignores this extension has performed and NOT rolled back — +1 on every confirmed ignore POST, whatever fired it (MI at drain time, EQ, DQ, and the curator drain via `bumpCount`, count-only), −1 on every confirmed `remove=1` POST (`dropCount`, in the drainer's one undo branch — droplist undo, solo-un-ignore gesture and badge click all drain through it). Both directions count the POST, never the intent: a dedupe skip, a region-lock skip or a refusal never posted, so it never moves. Still not the size of Steam's list — ignores made before install are not in it, which is also why the decrement is floored at 0 (rolling one of those back has no increment of its own to take back). The popup renders it as a link to `/account/notinterested/`, where the two numbers can legitimately differ |
| `ilap_ignored_history` | local | Last 20 ignored games. NAMED ignores only (MI/EQ/DQ) — the curator drain deliberately stays out: it enumerates appids with no names, and one job would flush the whole list. An un-ignore does not rewind it either: this is a log of what was ignored lately, and a rolled-back entry still happened (what is *undoable* lives in `ilap_ignore_log`) |
| `ilap_last_ignored_name` | local | Most recent game — written by the same named paths as the history, and equally untouched by the curator drain and by rollbacks |
| `ilap_shortcut_key` | local | Default ignore shortcut. Same vocabulary as the other two binding keys — the two swipes, `'zigzag'` (the circle), the three modifier-clicks — because any action may take any binding |
| `ilap_platform_key` | local | Already-Played shortcut, or `'off'`. Same vocabulary as above |
| `ilap_unignore_key` | local | Solo un-ignore binding: `'zigzag'` (default — hold right-click and draw a circle or a right-left zigzag over the capsule), any binding the ignore selects offer (`'swipeRight'`/`'swipeLeft'`/`'ctrlKey'`/`'shiftKey'`/`'altKey'`), or `'off'`. No legacy shim, unlike `normalizeShortcut`'s for the two ignore keys: this binding ships with its first release, so no build has ever written another vocabulary here. An unrecognised value (a hand-edited key) falls back to the default rather than becoming an inert binding: the content script clamps against `ManualIgnore.UNIGNORE_KEYS`, the popup select (which cannot reach that module) against its own `<option>` list. The vocabulary is IDENTICAL to `ilap_shortcut_key`/`ilap_platform_key`, so all three selects are cross-guarded against each other by disabling a value another one has taken (`syncSelectors`, asserted in `tests/popup/settings.spec.js`): resolution is first-match-wins in both `EventParser.parseClick` and `SwipeGestureDetector._fire`, with the ignore bindings resolved FIRST, so a value bound twice by a hand-edited storage key costs the rollback, not the ignore. `'off'` drops the rebindable gesture only: a **click on the IGNORED badge, either button, always un-ignores** — two delegated listeners in `manual-ignore/main.js`, answering to no setting but the master toggle (free, because the badge already swallowed plain clicks so it could not navigate). That is why the popup labels the option `shortcut_off_badge_only` ("Off - only Click on Badge") instead of the ignore selects' bare "Off". The zigzag is classified from the X axis ONLY, the same rule the swipe uses — so a clockwise and a counter-clockwise circle are indistinguishable and both fire; telling them apart would need `dy`, which is ruled out for these gestures. That is also why a flat left-right zigzag fires the binding: same motion to the detector, and genuinely useful on a capsule too short to circle over. Every locale's `shortcut_zigzag` label names the CIRCLE alone — one gesture per label, in a 320px row — so the zigzag is named nowhere in the UI. It used to live in a hover hint on the "Un-ignore:" row; that hint is gone (1.3.0), because naming one gesture per label is the rule the other two rows already follow and the hint fired on a label the user crosses on the way to the select under it. It is also resolved BEFORE the swipe: its legs clear the distance threshold on their own, so both would otherwise fire from one gesture |
| `ilap_mask_enabled` | local | Blur over the cover art of badged (ignored) capsules, ON by default — the MI toggle *Blur ignored covers*. Absent counts as ON, so only an explicit `false` turns it off (`ConfigService` seeds `maskEnabled: true`, and the popup reads `!== false`). Read live: `BadgeRenderer` applies `filter: blur` to the picked cover media, or lays a `.ilap-blur-backdrop` veil under the badge where the art is a CSS background; a write flips already-rendered badges in place through `syncMasks()`, without a reload |
| `ilap_master_enabled` | local | Global on/off. Two halves, and the split is the whole contract. **It stops the extension from ACTING**: `IgnoreGate.stopVerdict()` returns `'disabled'`, so every ignore source — the curator drainer (tab and SW alike), the EQ automator, the DQ icon click, the deferred MI/un-ignore jobs — is refused a slot and stops its pass (`src/background.js` also clears its retry alarm and parks on this key's next write, the only stop that is guaranteed to end with one). The MI gestures and the badge-click rollback are inert, and no new curator job can be staged. **And it removes what the extension DREW on Steam**: MI's IGNORED badges, their blur and backdrop veils (`IgnoreManager.hideBadges`, and `refreshAll` is gated so the storefront's mutation observer cannot repaint them); the EQ Queue-Helper toast, its card outline and micro-badge (`ActionUI.clearVisuals`) — an EQ teardown is deliberately equivalent to LEAVING the queue page, so re-enabling does NOT resume automation there, only a fresh entry to a `?queue=` page does (the queue's own `ilap_q_master` still resumes in place — but keyed on the TRANSITION `false`→`true`, and only on a page this key has never been seen off on (`_leftByMaster`, sticky for the page instance — an EQ advance is a full reload), whatever order the two switches came back in; a same-value restatement of this key, from a reset or a migration, vetoes nothing: `onChanged` fires for a write that leaves a value alone, and re-entering `run()` mid-flight is not a no-op); the DQ panel, which is unmounted and its loop stopped, and re-mounted on its idle Start state when the key comes back (`discovery-queue/main.js` gates on THIS key only — `ilap_q_master` is the Classic Discovery Queue's switch and does not reach the modal panel). That re-mount is a DEFAULTS reset, not a restore: `ui.mount` builds a fresh panel — unticked *Keep High Score*, green Start — so the teardown clears the automator's `skipPositive` with it (`_teardown`, shared with the modal-closed path), or the new panel's unticked box and the config behind it would answer differently and a run started from it would silently keep the positive games. Nothing about it is stored: *Keep High Score* is panel-lifetime state by design, and always has been; and the curator page's "Add to ignore queue" control, removed outright and re-injected live. (Those last two follow the key through `window.ILAP.MasterSwitch.watch`, `src/master-switch.js`.) **What it never touches is state**: nothing queued is dropped — curator, `mi`, `miundo` and `undo` jobs all sit where they were, with their cursors, and the drain resumes from them on re-enable (`onChanged` on this key kicks the drainer and the SW). The toggle writes this key and nothing else: stored job statuses are left exactly as they were — the queue array belongs to its serialized writers, and a rewrite from the toggle's context would race the drainer in another one. MI's per-tab session map survives too, which is why re-enabling repaints exactly the badges that were there. **And it is not allowed to lock the user out**: the widget (chevron, launcher, panel) is never master-gated — its own master toggle lives in the panel header, outside the dimmed `#ui-wrapper` — the surface switch (widget ↔ toolbar, and the `Ctrl+Alt+Shift+I` escape hotkey) keeps working, and the panel's IGNORE QUEUE applet stays live inside the dimmed wrapper: turning the extension off stops the drain, it must never prevent the user from REMOVING what is staged. Its Pause/Resume button is the one exception in the other direction — disabled while the master is off, so nothing can be started (see `ilap_curator_queue`). That exemption is why the panel dims the wrapper's CHILDREN one by one instead of the wrapper itself — a `filter`/`opacity` on an ancestor cannot be undone by anything inside it: `ui/popup_main.js` (`applyMasterInert` / `applyMasterDim`) sets `inert` and the `.master-dim` class on every child not marked `data-master-exempt` in the markup, so the exempt list lives in one place. Only `ilap_widget_pinned` goes inert with it (see below) |
| `ilap_dq_active` | local | Cross-tab cap on concurrently-active Discovery-Queue automators (`window.ILAP.Discovery.Registry`): a heartbeated owner map `{ ownerId: expiresAt }`, TTL-reclaimed like the curator lease so a closed tab frees its slot. `DiscoveryQueueController` claims a slot on Start (refuses with a transient "max {n} running" button message when ≥`CAP`=2 other live owners fill it), renews every 3 s while running, releases on stop. A UX bound, not a safety one — the `ilap_ignore_gate` governor already caps the aggregate POST rate; this just stops silent stacking of DQ loops. Cross-tab residual: no CAS, so two tabs racing can briefly make 3 active (accepted). Also accepted: Chrome throttles a backgrounded tab's timers, so a hidden DQ tab's heartbeat can lapse and its slot expire while its automator keeps ignoring (background loops run, slower) — the cap can undercount, but the rate gate still bounds the aggregate POST rate |
| `ilap_ignore_gate` | local | Aggregate ignore-POST rate governor (`window.ILAP.IgnoreGate`): a single last-reserved-slot timestamp. Every ignore SOURCE — the curator drainer (bulk curator jobs, `remove=1` undo jobs and deferred manual-ignore jobs alike, in a tab or in the service worker), the EQ automator, and the DQ icon click (which makes Steam's own page JS fire the ignore POST — confirmed, so DQ is NOT request-free) — calls `reserve()` before emitting an ignore; it advances this timestamp by ~500 ms + jitter (350 ms floor) via a per-context serialized RMW, so the aggregate rate across all tabs/sources of a profile stays ≤ ~2/s and stacked sources collapse into one paced stream. `reserve()` also STOPS (no slot) when `ilap_master_enabled=false` (closes audit #1: master vs drainer) or when there is no LIVE Steam session (closes audit #2: dead session must not burn work). The session check is deliberately NOT "is there a `sessionid` cookie?" — Steam hands that cookie to anonymous visitors too (it is a CSRF token, not a credential), so the old presence check was true on every store page of a signed-OUT browser and slots were granted for POSTs that could only 400; the cookie stays as the cheap precondition and the verdict comes from `SteamAuth`'s two signals: a signed-IN store header settles it for free (trusted in the positive direction only), otherwise one live `/account/` probe, cached in memory for 60 s (the SW has no DOM and always probes). Both stop conditions are RE-CHECKED after the pacing wait (a master flip / logout mid-wait can't be followed by one more ignore — DQ additionally re-checks `isRunning`, the drainer re-reads the job status, so a Stop/Pause during the wait stops before the POST). A stored slot further than `MAX_AHEAD` (30 s + `PENALTY_MAX`, since a 429 penalty from `ilap_ignore_gate_penalty` can legitimately push the slot minutes ahead) in the future is clock skew (manual clock change, resumed VM) and is clamped to now, not waited out. Manual ignore IS gated now: a swipe no longer fires an instant ungated POST but enqueues a `type:'mi'` job the drainer paces through this same governor, so the extension has no ungated ignore path left. `reserve()` takes an optional `{ foreground: true }` (EQ / DQ — see `ilap_ignore_foreground_at`); a background caller without it yields while visible work is recent. `stopVerdict()` — the same master/session check `reserve()` applies — is also exported, and the queue drainer calls it BEFORE opening a pass: a stopped extension would otherwise pay a `dynamicstore/userdata` GET per tab per standby tick (and keep the SW's retry alarm armed) only to be refused a slot afterwards. What this governor does NOT pace is the drainer's own `dynamicstore/userdata` dedupe GET at the top of a pass — it budgets POSTs. A pass is kicked by any storage write the drainer watches, this key's master flag among them, so flicking the extension off and on used to spend one such GET per flip per host; `MIN_PASS_GAP_MS` (2 s, `curator/drainer.js`) is the floor for that read, measured from the last pass that actually reached the network — a pass the gate stopped costs nothing and earns no gap, so re-enabling still drains at once. Kicks inside the gap are deferred, never dropped (one trailing re-kick answers for all of them; in the SW its retry alarm covers a timer that dies with the worker). Cross-tab residual: no CAS, so two tabs can rarely share a slot — accepted, same class as the stats/queue RMW races |
| `ilap_ignore_gate_penalty` | local | Rate-limit backoff for the ignore governor (`{ until, level }`), written by `IgnoreGate.reportRateLimited()` when the ignore endpoint answers **429** (`SteamAPI.ignore` now resolves `{ ok, rateLimited, retryAfterMs, status }` — `status` is the raw HTTP code (0 when the request never completed), read only by the curator drainer's 400-classifier so a timeout/5xx can't be mistaken for a region-lock refusal; the drainer ends its pass without burning `fails` on the appid, EQ reports and stalls — DQ can't see HTTP status, its POST is fired by Steam's page JS). `reserve()` folds an active `until` into the next slot, so every source in every tab goes quiet together; a source already HOLDING a reserved slot still fires it (accepted residual: ≤1 in-flight ignore per source after a 429). Escalation: 5 s doubling to a 5 min cap (`PENALTY_BASE`/`PENALTY_MAX`), honouring a numeric `Retry-After` up to the same cap; consecutive 429s escalate while each lands within `PENALTY_DECAY` (60 s) of the previous penalty's end, a quiet spell resets to level 1. An `until` further than `PENALTY_MAX` in the future is corruption/skew and is ignored (same rationale as the gate's `MAX_AHEAD`, which grew to 30 s + `PENALTY_MAX` so a legitimate penalty-pushed slot isn't clamped as skew). Cross-tab residual: no CAS, two tabs reporting the same 429 can double-escalate — accepted, over-backing-off is the safe direction |
| `ilap_ignore_foreground_at` | local | Timestamp of the last ignore reserved by a VISIBLE source — EQ or DQ, which pass `{ foreground: true }` to `IgnoreGate.reserve()`. A background reservation (the queue drainer, no flag) is refused with `reason:'yield'` while this stamp is younger than `YIELD_MS` (2.5 s, a little over one gap+jitter), so a stream of visible ignores keeps the drainer paused continuously while a lone one stalls it only a couple of seconds. Purely a priority split INSIDE the shared budget — it never raises the aggregate rate; the yielded pass retries on the standby tick / SW alarm. Manual ignore is not a foreground source any more: a swipe enqueues a `type:'mi'` job that the drainer picks FIRST (`_pickJob`) but still paces through the gate |
| `ilap_q_master` | local | Classic Discovery Queue (EQ) automator enable — the SETTINGS "Classic Discovery Queue" switch and the Queue Helper's *Disable*. Off stops automation and removes the toast but leaves the card's outline and micro-badge: it pauses the page rather than leaving it, and `run()` returns early on an already-processed card, so a stripped verdict would never be repainted on resume. Does NOT gate the DQ modal panel, which answers to `ilap_master_enabled` only |
| `ilap_q_next` | local | Auto-advance after ignore |
| `ilap_q_mode` | local | `"bad"` or `"all"` |
| `ilap_dq_open` | local | SETTINGS panel: "Classic Discovery Queue" subcategory expanded (default collapsed). Restored on each settings render, persisted on `<details>` toggle. Mutually exclusive with `ilap_mi_open` — opening one collapses the other |
| `ilap_mi_open` | local | SETTINGS panel: "Manual Ignore" subcategory expanded (default collapsed); mutually exclusive with `ilap_dq_open` |
| `ilap_settings_open` | local | The SETTINGS accordion itself, open or closed (`ui/popup_main.js`) — the parent of the two above, restored on render and written on every `<details>` toggle. Both surfaces share it: a panel opened in the widget is open in the toolbar popup too |
| `ilap_lang` | local | UI language, an entry of `i18n.LANGUAGES` (absent = `'en'`). Written by the language chip in the SETTINGS summary, and read by `src/i18n.js` at boot in all three worlds; a code with no dictionary falls back to `'en'` rather than showing keys. Every world also FOLLOWS the key: `setLang` fires the `onLangChange` subscribers, which is how an on-page UI already drawn (the curator button, the DQ panel) redraws its labels without a reload |
| `ilap_session_map_v2` | session | appid → reason map |
| `ilap_queue_active` | session | Explore queue ACTIVE intent |
| `ilap_queue_ff` | session | Explore queue fast-forward intent |
| `ilap_queue_nav_token` | session | 15 s navigation authorization token |
| `ilap_queue_active_appid` | session | The appid the ACTIVE/FF intent above belongs to (`NavigationGuard`). It is what tells a RELOAD of the queue page the automation is running on (legitimate — the intent survives) from a sideways jump to another `?queue=` page with no nav token (not — the automation resets and re-prompts). Cleared with the rest of the intent by `resetState` |
| `ilap_curator_queue` | local | The ignore queue: an array of jobs holding user-owned fields only, every write through `Store.mutateQueue`. Four job types; at most `MAX_JOBS` (3) curator and undo jobs, plus the two gesture jobs outside that cap. Drain progress lives in the cursor keys, "running" in the drain lease. See [The job queue](#the-job-queue) below. |
| `ilap_ignore_log_index` + `ilap_ignore_log_c<seq>` | local | Undo data source (`window.ILAP.IgnoreLog`): append log of every ignore the EXTENSION performed — `{ appid, name?, ts, source: mi\|eq\|dq\|curator, curatorId?, undoneAt?, skipped? }`, FIFO-capped at 5000. Stored in CHUNKS of 100 entries: the index `{ first, last }` names the live chunk sequence numbers, the log is those chunks concatenated oldest → newest, an append writes only the tail chunk (a new one once it is full), and the cap retires whole chunks from the head (so a full log holds 4901–5000 entries). One array written whole per POST handed hundreds of KB, old AND new value, to every `onChanged` listener in every tab 1–3×/s mid-drain; `markUndone` likewise rewrites only the chunks holding the appid. Read it through `IgnoreLog.getLog()`, never from a storage snapshot; `IgnoreLog.isLogKey(k)` tells a log write apart. The single-array `ilap_ignore_log` of earlier builds is migrated lazily by the first log access in any world (the SW migration script is not in the test build): an array found there becomes the log and the key is removed — it REPLACES any chunks, which only a spec seeding the legacy key can put next to it. A `skipped` marker records an appid a drain stepped over WITHOUT ignoring it (a refusal, NOT an ignore) — inert for every undo selector, kept as the durable "the job wasn't a full done" trace: `'unavailable'` for a region-locked appid (classified 400), `'failed'` for one that lost every retry on a live session. That second value is the ONLY trace of the `MAX_FAILS` path — the per-job `ilap_curator_skipped_<id>` counter dies with the job and the push cards need a listening tab, which the SW route has none of by design (no notification surface was built for it, deliberately). Costs no extra volume — an appid that had landed would have been appended here anyway. MI entries carry the swipe-time `name` on both paths; UNDO jobs never write a `skipped` entry, because a failed rollback's log entry must stay live so the next "undo the last N" retries it. Written beside `saveStats` by the MI/EQ/DQ stats adapters (they pass the appid through) and by the curator drainer per confirmed ignore (appid-only — enumeration has no names). Steam's own `rgIgnoredApps` carries no dates, so count- AND time-scoped undo both operate on OUR `ts`. The undo drainer marks rolled-back entries `undoneAt` (kept, not deleted) so a later undo can't re-undo them and the curator droplist can warn on a re-stage within 48 h (`lastUndoneForCurator`); inverse-dedupe skips (appid already un-ignored elsewhere) are marked too, so stale entries can't inflate the undoable count forever. Undo deliberately does NOT touch `ilap_ignored_count`/history (curator drains never incremented them — a decrement would corrupt). Serialized writes; cross-tab no-CAS residual accepted (at worst one log entry lost, cosmetic). Drain-progress keys for the popup render path (written 1–3×/s mid-drain → only the undo applet re-reads the log) |
| `ilap_curator_cache` | local | Per-curator enumerated apps cache (TTL 7 d, LRU ≤10). Only a run that COVERED the list is cached: a read that failed part-way, one stopped by our own page ceiling, and one that parsed no rows at all while the server reported some (a markup change under `parseResults`) are all `partial`, and a partial run is used for the job at hand but never stored — the cache is keyed by curator alone, so a short or empty run would be served for the whole week and every re-add inside it would fail the same way without touching the network |
| `ilap_curator_cursor_<jobId>` | local | Drainer-owned per-job progress cursor (single writer = lease holder; removed with the job, or with its old id when a filter switch re-files the job under a new one — `EnqueueService.stage`, so a drainer mid-iteration on the old list finds its job gone instead of POSTing an old entry or advancing the new list). `Store.setCursor` refuses the write when the job is no longer in the queue, so a remove racing a resolve/drain iteration can't recreate (leak) the key after its only cleanup path ran — and the drainer re-reads the queue before that write for any job whose id is REUSED (`job_mi`, `job_mi_undo`) or whose pass is an undo, because there a leaked key is not garbage but a silent failure: the next job of that id mounts past its own end. Written far faster than a POST rate during a dedupe run (skips are not gate-paced), which is why the popup applet renders progress on a trailing 1 s throttle while every other queue change stays immediate |
| `ilap_curator_skipped_<jobId>` | local | Drainer-owned per-job count of appids skipped as permanently refused (400 classified as region-locked via an appdetails probe: no store object in the account's region). Same single-writer/partitioning/cleanup discipline as the cursor key; surfaced in the queue applet's job row |
| `ilap_curator_lock_<id>` | local | Per-job drain lease `{ owner, expiresAt }` (single-drainer handoff, `src/curator/lease.js`); a live lease is also the UI's derived "running" signal |
| `ilap_curator_pulse` | local | Timestamp written when a job finishes; widget watches it to blink once (finished jobs are removed, not kept) |
| `ilap_unignored` | local | `{ appids: [...], ts, reason }` pulse written whenever games stop being ignored (`Store.signalUnignored`): after EACH confirmed `remove=1` of an undo drain (`reason:'undo'`), when a deferred Manual-Ignore POST is dropped for good — region-locked appid or every retry refused (`reason:'failed'`), and when an MI job is REMOVED from the queue applet with entries still undrained (`reason:'removed'` — silent, the user asked for exactly this; the whole tail from the cursor on — the `mi_queue_stuck` card tells the user to do exactly that, and those POSTs will now never fire), and when a solo un-ignore gesture CANCELS a swipe that was still queued (`'undo'` — nothing was ever ignored, so there is nothing to tell the user). That last one goes through the pulse rather than un-badging in place precisely because badges are per-tab AND persisted in `sessionStorage`: a second tab that swiped the same game would otherwise keep showing IGNORED for a swipe that was taken back, across reloads, until the tab was closed. Every Manual-Ignore content script watches it via `onChanged` and clears those games' on-page IGNORED badges (`BadgeRenderer.unrender` + drop from the per-tab `sessionMap`) — only for appids THIS tab badged. `'failed'` additionally raises the shared push card (`mi_ignore_failed`), once per burst, so an optimistic badge never just evaporates minutes after the swipe; `'undo'` and `'removed'` stay silent, the user asked for both. Listeners also accept the pre-list `{ appid }` payload, so an already-open tab still running the OLD content script across an extension update does not keep a badge that lies until it is reloaded. The payload is a LIST: the drainer still pulses one appid at a time (so a badge rolls back as its game does), but a removed job drops its whole tail in one write rather than N onChanged fan-outs. `removeJob` reads the cursor AFTER the queue write — `setCursor` refuses once the job is gone, so the drained head can't be un-badged by a concurrent advance |
| `ilap_undo_failed` | local | `{ ts, reason }` pulse (`Store.signalUndoFailed`), the mirror image of a `'failed'` un-badge: a rollback the user asked for is not going to happen, so the game stays ignored. No appid — nothing on the page is wrong (the badge says "ignored", which it is); the point is that the rollback silently didn't happen, and the only other trace was a job-row skip line that dies with the finished job. `reason` carries the SAME distinction as `ilap_unignored`'s: `'failed'` (an UNDO job's `remove=1` was permanently refused for a region-locked appid, or failed every retry) raises the card; `'removed'` (the user dropped the whole `miundo` job from the queue applet) clears the pending marks and stays SILENT, because "Steam refused some rollbacks" would blame Steam for what the user just did. Any store tab turns a `'failed'` pulse into one throttled `undo_failed` push card (the Manual-Ignore content script owns the listener — it is the only module on EVERY store page with a push card; the curator module no-ops outside a curator page). It is also what takes the pending mark off badges whose SOLO un-ignore fell through: the pulse carries no appid, so every pending mark in the tab clears — worst case a droplist undo's failure un-dims a solo gesture that is still queued, which leaves the badge saying the true thing either way. Like the MI `'failed'` card, a drain with no tab open loses the notice (deliberate) |
| `ilap_sw_sid` | local | Cached `sessionid` for the SW drainer (`src/background.js`, Chromium only): under `permissions: ["storage"]` the service worker cannot read `document.cookie`, so `src/sw-handoff.js` caches the cookie here on every store page. Change-only write (a same-value write would wake the SW via `onChanged` for nothing); written at page boot rather than enqueue time so a re-login refreshes it. The SW mirrors it into memory (the gate's `getSessionID` reads it synchronously); no value → the gate's `no-session` stop applies. The SW also REAPS it: a `probeLogin` that comes back a definite `false` clears the key, since a sid Steam no longer honours is a token with no use left (a failed probe is not evidence and clears nothing). Firefox does not write this key at all — `src/sw-handoff.js` is left out of that manifest on purpose: there is no SW drain there to read it, and no reaper either, so the page would be caching a token nothing consumes and nothing clears. Builds before 1.3.0 DID write it there, and dropping the script only stops new writes — an upgraded profile would keep the last copy forever, with nothing left to read it or clear it. So `src/migrate.js` reaps the pair (`ilap_sw_sid` + `ilap_sw_halt`) at load wherever `chrome.alarms` is absent: that API is what the Chromium drain paces itself with, so no alarms ⇒ no drain ⇒ no reason to hold a session token. Top-level, not in `onInstalled` — it must not depend on catching one event in one lifetime; removing an absent key writes nothing and fires no `onChanged`, so a Chromium-shaped profile and a clean Firefox one both pay nothing |
| `ilap_sw_halt` | local | SW-drain circuit breaker: set true by the SW after 2 CONSECUTIVE failed ignore POSTs (429s excluded — that's the gate penalty's job; 400s classified as region-locked appids excluded too — they're per-appid, not systemic, and are skipped/counted instead, so the "open a store page" hint stays truthful). A stale cached sid (re-login with no store tab open) or a missing `Steam_Language` cookie fails EVERY POST, and the drainer's `MAX_FAILS` (3) skip would then burn appids one by one; the halt engages at 2 — before the first skip — and the SW's gate wrapper refuses every slot while it's set. Cleared by the drainer boot on any store-page visit, which also re-caches the sid (one user action fixes both causes; the popup queue applet shows a `queue_sw_halt` hint pointing there). Also cleared by the worker's own HOURLY retry alarm while work is still queued: a failed POST cannot tell a stale sid from a twenty-second network drop, and failing closed on both is deliberate — but with no tab open nothing would ever produce the store-page visit, so the queue would sit halted for good, silently. The retry costs at most two refused POSTs (the halt engages below `MAX_FAILS`, so no appid is burned) and re-halts for another hour if the cause was permanent. Tab drainers ignore the flag — their cookie jar is live |
| `ilap_widget_expanded_ts` | local | Widget launcher state: 0/absent = collapsed to the chevron tab (default); >0 = expanded, value = last-activity timestamp (bumped on widget clicks, throttled 5 s). Any tab's 60 s idle timer stashes the launcher; an open panel re-bumps instead |
| `ilap_widget_pinned` | local | Widget pin badge (launcher corner, shown on hover): true = launcher pinned out — idle timers re-bump instead of stashing, stale-timestamp mounts stay expanded — until the user unpresses the pin. Gated by `ilap_master_enabled`: while the extension is disabled the pin goes inert (`.ilap-pin.disabled` — greyed + `pointer-events:none` + a click-handler guard), reveals on a launcher hold so its state stays visible but can't be toggled; the rest of the widget (chevron, launcher, panel, master toggle) is NOT master-gated so the extension can always be re-enabled from the panel |
| `ilap_surface_mode` | local | Which surface hosts the popup UI: `'widget'` (default) = on-page shadow-DOM widget; `'popup'` = the `chrome.action` toolbar popup (`ui/popup.html`). In popup mode the on-page widget parks to a ghost-chevron beacon. ## The job queue

`ilap_curator_queue` in detail.

### Types

Every job's `type` is one of `Store.JOB_TYPE`. Read it through `Store.jobType()`,
never `job.type`: a curator job staged before the field existed has none and
reads as `curator`. `Store.jobTraits()` answers the two questions the code asks
of a type (`undo`, `gesture`); what each type does at POST, landing and drop is
one policy table in `curator/drainer.js` (`policiesFor`). The drainer and both
staging services read this vocabulary off the store they are handed.

| Type | Record | Count | Filled by |
|------|--------|-------|-----------|
| `curator` | `curatorId`, `filter`, `appids`, `status` (enumerating / pending / paused) | under the cap | the curator-page button (`EnqueueService`) |
| `undo` | `curatorId:'undo'` (keys its lease), a STATIC `appids` snapshot of `ilap_ignore_log`, `snapshotTs` | at most one, under the cap | the popup undo droplist (`UndoService`) |
| `mi` | id `job_mi`, `curatorId:'mi'`, `appids` + `meta[appid] = {name, reason, cancelled?}` | at most one, outside the cap, `MI_MAX` 200 | ignore swipes (`Store.enqueueMi`) |
| `miundo` | id `job_mi_undo`, `curatorId:'miundo'`, `appids` + `meta[appid] = {ts}` | at most one, outside the cap, `MIUNDO_MAX` 200 | solo un-ignore gestures (`Store.enqueueMiUndo`) |

- **The cap.** `Store.cappedCount(queue)` counts what `MAX_JOBS` limits: every
  job but the two gesture types. Both staging services compare that, never
  `queue.length`, so a pending swipe never costs a curator slot.
- **Unknown type** (after a downgrade): no traits. The drainer never picks it
  (it could be a rollback), the rest drains past it, the applet only offers
  Remove, and it counts under the cap.
- **Priority.** `miundo`, then `mi`, then background work (`_pickJob`). A job
  drains to its end, so the gesture jobs cannot share one: a rollback is the
  later intent and holds a provisional mark on screen, so it goes first.
- **Direction is per job.** The drainer reads `undo` off the type for the whole
  pass (strict userdata read, login probe on an empty set, inverted dedupe, "last
  intent wins"), which is why a rollback is its own job, not a flag on an MI entry.

### Gesture jobs

- Auto-created on the first gesture, auto-deleted when drained empty. A swipe no
  longer POSTs: it badges optimistically and appends. `appids` stays a plain
  string array; per-entry data lives in `meta`.
- A re-swipe of an appid still pending is de-duped but REFRESHES its meta: a
  second tab may swipe the same game with the other reason, and the queued POST
  must match the badge. Rewriting the entry also clears a cancel mark.
- Past `MI_MAX` / `MIUNDO_MAX` a gesture is a no-op and raises that job's own
  "queue stuck" card.
- `miundo` entries carry their own gesture time in `meta[appid].ts`: a job-level
  time would be the first gesture's, and a game ignored after it and un-ignored
  by a later gesture would read as "re-ignored after the snapshot".
- Stats and Last Ignored (`saveStats`, `log.append(source:'mi')`) are written at
  drain time, and only for `mi`.

### Cancelling an unsent swipe

A solo un-ignore aimed at a game whose ignore is still pending marks
`meta[appid].cancelled` (`Store.cancelMiEntry`) instead of queueing a rollback.
It is tried before the un-ignore cooldown and the login gate: a cancel sends no
POST, so there is nothing to brake and no session needed.

- It MARKS rather than splices: `appids` indices are the cursor's coordinates.
- The drainer checks the mark before spending a rate slot and again on the fresh
  record after the gate wait, where a cancel usually lands. A cancelled entry
  sends nothing and is neither logged nor counted.
- `cancelMiEntry` re-reads the cursor after the mutation and reports false if the
  drain got there first; the tab then queues a real rollback.
- The cursor advances only after the POST returns, so a cancel landing mid-request
  is told it succeeded. The drainer closes that window: after advancing, it
  re-reads the mark and queues the un-ignore itself (`_compensateCancelled`). The
  ignore did land, so it stays counted and logged.

### Undo passes

Undo jobs share the lease, handoff, cursor key, Pause/Remove and gate pacing,
and POST `remove=1`. The dedupe is inverted: an appid absent from userdata is
skipped and its log entries marked `undoneAt`. That makes an empty set dangerous:

- A failed strict userdata read STOPS the pass (job intact, retried later).
- An empty set is trusted only after a live `SteamAuth.probeLogin()`: a
  logged-out read returns the same empty defaults.
- `rgIgnoredApps` lags a fresh ignore by seconds, so an appid whose newest log
  entry is within `UNDO_FRESH_MS` (~15 s) is un-ignored anyway (`remove=1` is
  idempotent).
- Removing a `miundo` job with entries left pulses `ilap_undo_failed` with
  `reason:'removed'`: the pending marks come off, silently.

### Master switch

While the global master is off, the applet's Pause/Resume is disabled (in `_row`,
plus an `_onAction` guard for a render-vs-click race); jobs can only be removed.
The master toggle never writes this key: a whole-array rewrite from the popup
would race the drainer's `removeIfDrained` in another context and could
resurrect a job it just finished.
